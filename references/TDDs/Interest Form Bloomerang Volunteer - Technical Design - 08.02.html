What breaks a tie

Security › Reliability › Speed

The Volunteer API key is a full org Bearer token (create users and list them). Anything that weakens secret isolation or opens a spam write path loses, even if it ships faster.

§

Two Bloomerang products — do not conflate

Bloomerang CRM (bloomerang.co) has Bloomerang.js and a public pub_ key safe for client forms. Bloomerang Volunteer (volunteer.bloomerang.co) has only a server-side Bearer API. This design is Volunteer-only. A CRM interest path would be a separate decision.

Context

How it works today

  • tccane-website-v2 is a zero-dependency static site (index.html, styles.css, app.js). No backend, no build step.
  • Get Involved (#involved) is outbound-only today: advisor mailto:, Instagram, Discord.
  • An approved July design planned CRM + Bloomerang.js client posts. That path does not write to Volunteer.

Binding constraints

These bind every choice below

  • Bearer token is secret — never embedded in static JS, HTML, or client bundles.
  • Gateway is least-privilege: implement only POST create-user proxy logic; no passthrough of arbitrary Volunteer paths.
  • Form collects only first name, last name, email in v1.
  • Destination is Volunteer org membership only — not CRM interactions, not event shifts.
  • Site remains plain HTML/CSS/vanilla JS at the edge (no SPA framework required for the form).
  • Priorities: Security > Reliability > Speed-to-ship.
01

Gateway placement on Cloudflare

At stake: Where the privileged write path lives relative to the static site drives deploy model, same-origin vs CORS, and how secrets attach. Forced by “Workers host the API” plus today’s zero-backend site.

ACF Pages + Pages FunctionRecommended

Host the static site on Cloudflare Pages. Add a Pages Function at /api/interest (Workers runtime). Form posts same-origin.

Same-origin (no CORS surface). One project, one deploy. Secrets via Pages env. Idiomatic for static + one API route.

Moves site hosting onto Cloudflare (or dual-publishes). Pages Function limits apply (usually fine at chapter volume).

BStandalone Worker (API only)

Site stays on current static host. Separate Worker at e.g. api.… or *.workers.dev. Form POSTs cross-origin.

Site hosting unchanged. Clear service boundary. Full Workers feature set without Pages coupling.

CORS must be locked to the real origin(s). Two deploy pipelines. Easy to misconfigure Access-Control-Allow-Origin: *.

CWorker serves static + API

One Worker with static assets binding (or Workers Sites) plus the API route.

Single runtime unit; full control of headers and routing.

Reimplements static hosting we get free from Pages. Higher ops for no security gain over A.

Recommendation

ACloudflare Pages + Pages Function at /api/interest

Wins on Security (no CORS misconfig class) and low ops, without sacrificing the Workers runtime the requirement named. Assumption: hosting the static site on Cloudflare Pages is acceptable. If the site must remain off CF, fall back to B with a strict origin allowlist and no wildcard CORS.

02

Protecting the public write endpoint

At stake: Anyone who can hit the gateway can attempt to create Volunteer users with a privileged org token. Weak controls mean spam accounts and, if the Worker is ever over-proxied, roster exfil. Forced by Security-first and the absence of a client-safe public key.

ATurnstile + rate limit + least privilegeRecommended

Cloudflare Turnstile on the form; server verifies the token. CF rate limiting (or in-Worker fixed window per IP). Worker accepts only a strict JSON schema and only calls Volunteer POST .../users.

Strong bot resistance; CF-native; free tier sufficient; pairs with honeypot as defense-in-depth.

Adds Turnstile script + sitekey; one external dependency at submit time.

BHoneypot + time-trap + rate limit only

July-design style: hidden field, min elapsed ms, IP rate limit. No CAPTCHA/Turnstile.

Zero third-party script; fastest UX; matches prior design intent.

Weaker against motivated bots. Conflicts with Security as top priority on a privileged write proxy.

CAuth-gated submit (login / magic link)

Require the submitter to prove email ownership before the Worker calls Volunteer.

Highest assurance the email is real; reduces junk usernames in VMS.

Kills low-friction “express interest” UX; out of scope for a three-field form.

Trade-offs
Dimension A — Turnstile + RL✓ recommended B — Honeypot only C — Verify email first
Bot / abuse resistanceStrongWeak–moderateStrong
Fit to Security priorityAlignedUnder-protects token proxyAligned but heavy
UX frictionLow (invisible Turnstile mode)NoneHigh
Build effortModerateLowHigh
Least-privilege WorkerRequired either wayRequired either wayRequired either way
Recommendation

ATurnstile verification + rate limit + schema-strict, single-route Worker

Security is the tie-break. Keep honeypot + time-trap as cheap defense-in-depth (from the July design), not as the primary control. Worker hard-rules: no generic reverse-proxy; reject unknown fields; never implement GET user list.

03

Failure handling when Volunteer is down

At stake: Whether a Volunteer outage or 5xx drops a lead forever, or the system absorbs it. Forced by Reliability as second priority and low expected volume (chapter interest, not viral traffic).

ASync-first + durable dead-letterRecommended

Worker tries Volunteer synchronously. On success → 200 to browser. On transport/5xx failure → write payload to CF Queue (or KV/D1 dead-letter), return 200/202 “received”, retry via consumer or cron. Validation/4xx from Volunteer → 4xx to client (fixable).

Happy path lands in VMS immediately for advisors. Failures are not silent drops. Matches Reliability without always-async complexity.

Need a small retry worker/cron and ops eyes on the dead-letter. User may see success before VMS shows them (seconds–minutes).

BSync only + mailto fallback

July pattern: if post fails, reveal pre-filled advisor mailto:. No server-side buffer.

Minimal infra. User can still reach a human.

Depends on user completing mailto. Silent loss if they close the tab. Weaker on Reliability.

CAlways-queue (async only)

Every valid submit enqueues; consumer always calls Volunteer. Browser always gets fast 202.

Maximum decoupling; uniform code path; easy retries.

No immediate VMS visibility; more moving parts for low volume; harder to surface “email already in org” nuances synchronously.

Trade-offs
Dimension A — Sync + DLQ✓ recommended B — Sync + mailto C — Always queue
Lead durabilityHighUser-dependentHigh
Time-to-visible in VMSImmediate on happy pathImmediate if OKEventual
Infra complexityModerate (Queue or KV+cron)LowestModerate–high
Fit to Reliability priorityAlignedGaps if user bailsAligned
Fit to low volumeAppropriateOKSlightly heavy
Recommendation

ASynchronous Volunteer POST with durable dead-letter + retry

Reliability without giving up immediate VMS writes. Prefer CF Queues if the account has them; otherwise KV list + scheduled Worker is enough at chapter scale. Keep mailto as a last-resort UI only when the Worker itself is unreachable (static fallback), not as the primary durability story.

System architecture

Path of an interest submission

Browser posts to a same-origin Pages Function. The Function verifies Turnstile, validates input, calls Bloomerang Volunteer with the server-held Bearer token, and dead-letters transient failures for retry.

Data flow (numbered)

  1. User fills first name, last name, email on the Get Involved card.
  2. interest-form.js runs client validation and spam gates; requests Turnstile token.
  3. Browser POST /api/interest with { firstName, lastName, email, turnstileToken } (honeypot empty).
  4. Pages Function verifies Turnstile with Cloudflare siteverify; applies IP rate limit.
  5. Pages Function builds { username: email, firstName, lastName }.
  6. Pages Function calls Volunteer POST /v4/organizations/{org_id}/users with Bearer token.
  7. Volunteer creates user or attaches existing email to org; returns user object array.
  8. Pages Function returns success JSON; UI shows confirmation.
  9. On Volunteer 5xx/network error: Function writes DLQ record and still acknowledges receipt to the user; retry consumer re-POSTs until success or poison threshold.
