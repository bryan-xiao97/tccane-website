Goal

Purpose

Replace Bloomerang Volunteer as the destination for interest submissions with Google Sheets as a temporary operational datastore. The change is intended to provide a simpler interim destination while preserving the existing submission workflow.

Success criteria

  • Every valid submission creates one complete Google Sheets row or is durably retained for retry.
  • A completed submission appears no more than once for the same generated submission identifier, including after ambiguous network failures.
  • The public submission endpoint retains its existing request contract and user-facing validation, abuse controls and failure-handling behavior.
  • No active source, test, configuration, example or current README instruction depends on Bloomerang.
  • The integration remains administratively viable when an individual maintainer leaves the organization.

Non-goals

  • Redesigning the interest form or its request payload.
  • Building reporting, dashboards, downstream automation or staff-editing workflows.
  • Creating spreadsheets or repairing headers automatically at runtime.
  • Using Apps Script or a command-line process as the production write path.
  • Deleting dated design documents, implementation plans or session records that mention Bloomerang.
  • Turning Google Sheets into a permanent system of record.

Hard constraints

  • The write path remains in the existing Cloudflare Pages Function.
  • Google access uses a service account and google-auth-library.
  • The Google Cloud project is organization-managed and has at least two administrators.
  • The spreadsheet is pre-provisioned, organization-owned and shared directly with the service account as Editor.
  • The solution prioritizes maintainability and reliability over the smallest possible change. There is no fixed delivery deadline.

Desired end-state

Submission behavior

  1. A client sends the existing interest payload to POST /api/interest.
  2. The current method, configuration, payload, rate-limit and Turnstile gates remain in force.
  3. After those gates pass, the server assigns one opaque submission ID and one UTC submission timestamp.
  4. The server requests a service-account access token through google-auth-library using credentials held only in an encrypted Cloudflare secret.
  5. The server appends one row to the configured Submissions table through Sheets API v4. The request uses row-major values, raw input interpretation and inserted rows so form strings are not evaluated as formulas or allowed to overwrite adjacent content.
  6. A confirmed append returns an HTTP success response with status recorded.
  7. A retryable Google or network failure stores the same submission ID, timestamp and business fields in the existing durable queue, then returns status accepted only after the queue write succeeds.
  8. Before a queued retry appends, it checks the sheet's submission ID column. An existing ID completes the retry without another append. A missing ID allows the append to proceed.

Operational ownership

  • The Google Cloud project sits under the organization's managed resource hierarchy and has at least two administrators.
  • The service account is application identity, not document ownership. It receives Editor access only to the intended spreadsheet.
  • The spreadsheet is owned by a stable organization identity or Shared Drive and contains a manually managed Submissions tab with the exact header contract.
  • Credential replacement does not require data migration. A replacement service account can be shared onto the same sheet before the old credential and permission are revoked.
  • Current standard usage remains far below published Google quotas and does not require a quota increase.

Observable completion

  • Each accepted test submission is represented by one five-cell data row with a unique ID and UTC timestamp.
  • Replaying the same queued submission ID does not create a second row.
  • Destination outages leave valid submissions in the durable queue rather than silently losing them.
  • Active runtime behavior, tests, configuration, environment examples and current operating documentation refer only to Google Sheets as the destination.
  • Dated historical artifacts remain available and clearly function as history rather than current operating guidance.

Explicitly out of scope after completion

Google Sheets remains a temporary datastore. The completed change does not provide record editing rules, reporting, CRM synchronization, lifecycle retention, automatic schema migration, sheet creation, form redesign or a permanent database strategy.

Assumptions & open questions

  • Assumption: TCCANE has or can establish a Google Workspace or Cloud Identity organization that can own the Cloud project and provide at least two administrators.
  • Assumption: Organization policy permits creation of a user-managed service-account key. Some newer Google Cloud organizations disable key creation by default. If prohibited, the service-account authentication mechanism must be revisited without changing the chosen Sheets API destination.
  • Assumption: The organization can store the credential as an encrypted Cloudflare secret and maintain a rotation procedure outside the repository.
  • Assumption: google-auth-library operates in the deployed Pages Function with Cloudflare's Node compatibility mode. This is supported by the documented runtime capabilities but remains an environment compatibility assumption until exercised in that project.
  • Assumption: The expected volume remains near the prior limit of 100 submissions per day. The chosen retry-time ID-column lookup is intentionally optimized for this low-volume temporary datastore.
  • Open question: The final organization identity or Shared Drive that will own the spreadsheet has not been named.
  • Open question: The final Google Cloud project ID, service-account name, spreadsheet ID and deployed tab name have not been assigned.
  • Open question: Google's documentation says over-quota charging is planned later in 2026. This does not affect the expected volume, but the pricing statement should be rechecked if usage or Google policy materially changes.
